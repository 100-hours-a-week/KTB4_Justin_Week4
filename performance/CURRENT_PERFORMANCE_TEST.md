# TuneLog 현재 성능 테스트 결과

## 1. 목적

N+1 개선과 게시글 카운터 비정규화가 반영된 현재 `develop` 코드에서 다음 두 가지를
간단하게 확인했다.

1. 페이지 크기가 증가해도 게시글 목록 SQL 수가 증가하지 않는지 확인
2. 기존과 동일한 대용량 데이터에서 소규모 읽기·쓰기 부하가 오류 없이 처리되는지 확인

운영 RDS가 아니라 별도의 로컬 MySQL `tunelog_performance` 데이터베이스만 사용했다.

테스트 일자: 2026-08-06

---

## 2. 테스트 데이터

이전 성능 테스트에서 생성한 데이터를 그대로 사용했다.

| 데이터 | 개수 |
|---|---:|
| 게시글 | 50,000 |
| 게시글 이미지 | 25,000 |
| 좋아요 | 150,000 |
| 댓글 | 150,000 |

성능 테스트 DB가 첫 N+1 개선 당시 스키마였으므로 현재 코드에 맞게 다음 작업을 먼저
적용했다.

```text
posts.image_url 추가 후 기존 이미지 25,000건 백필
posts.like_count 추가 후 좋아요 150,000건 집계·백필
posts.comment_count 추가 후 댓글 150,000건 집계·백필
인기순·장르 인기순 인덱스 추가
백필 검증 후 post_images 제거
```

검증 결과는 다음과 같다.

```text
SUM(posts.like_count)    = COUNT(post_likes) = 150,000
SUM(posts.comment_count) = COUNT(comments)   = 150,000
posts.image_url NOT NULL = 기존 이미지 수    = 25,000
```

## 3. 측정 방법

### 3.1 SQL 수

성능 테스트 Profile에서 Hibernate `StatementInspector`로 요청 중 실행된 SQL을
계수했다.

```text
HTTP 요청 시작
→ ThreadLocal SQL 카운터 초기화
→ Hibernate가 SQL을 실행할 때 SELECT/INSERT/UPDATE/DELETE 분류
→ 응답 헤더에 SQL 수 기록
```

사용한 응답 헤더:

```text
X-SQL-Count
X-SQL-Select-Count
X-SQL-Insert-Count
X-SQL-Update-Count
X-SQL-Delete-Count
```

목록은 `size=10`, `50`, `100`을 각각 실제 요청해 페이지 크기에 따른 SQL 수 변화를
확인했다.

### 3.2 간단한 부하 테스트

Artillery를 이용해 로컬 Spring Boot 서버에 요청했다.

```text
읽기: 20개 사용자 흐름 × 10개 API = 총 200요청
쓰기: 3개 사용자 흐름 × 20개 API = 총 60요청
```

읽기 흐름에는 장르, 최신·인기·장르별 게시글, 상세, 댓글, 사용자, 좋아요 목록을
포함했다.

쓰기 흐름에는 회원가입·로그인, 업로드, 게시글 작성·수정·삭제, 댓글 작성·수정·삭제,
좋아요 추가·삭제, 사용자 수정·탈퇴를 포함했다.

테스트 중 메모리 여유 비율이 10% 아래로 내려가면 중단하도록 했으며 실제 측정에서는
34~36%를 유지했다.

## 4. SQL 수 결과

### 4.1 게시글 목록

| API | SQL | 구성 |
|---|---:|---|
| 공개 최신 10개 | 2 | 목록 SELECT + 전체 COUNT |
| 공개 최신 50개 | 2 | 목록 SELECT + 전체 COUNT |
| 공개 최신 100개 | 2 | 목록 SELECT + 전체 COUNT |
| 로그인 최신 10개 | 3 | 공개 목록 SQL + 현재 페이지 좋아요 여부 |
| 로그인 최신 50개 | 3 | 공개 목록 SQL + 현재 페이지 좋아요 여부 |
| 로그인 최신 100개 | 3 | 공개 목록 SQL + 현재 페이지 좋아요 여부 |
| 공개 인기순 10개 | 2 | `like_count` 정렬 목록 + 전체 COUNT |
| 공개 ROCK 장르 10개 | 2 | 장르 목록 + 전체 COUNT |

페이지 크기가 10개에서 100개로 증가해도 SQL 수는 증가하지 않았다.

```text
개선 전 공개 목록: 42 → 202 → 402
현재 공개 목록:     2 →   2 →   2

개선 전 로그인 목록: 43 → 203 → 403
현재 로그인 목록:     3 →   3 →   3
```

### 4.2 단건과 댓글

| API | SQL | 구성 |
|---|---:|---|
| 공개 게시글 상세 | 2 | 조회수 UPDATE + Post/User SELECT |
| 로그인 게시글 상세 | 3 | 공개 상세 SQL + 좋아요 EXISTS |
| 댓글 첫 페이지 | 2 | Post EXISTS + Comment/User SELECT |
| 좋아요 모아보기 첫 페이지 | 1 | Post/User SELECT |

댓글과 좋아요 모아보기는 테스트 계정의 첫 페이지 데이터가 페이지 크기보다 적어
Spring Data가 별도 COUNT 쿼리를 생략했다. 페이지가 가득 차거나 다음 페이지가
필요하면 COUNT가 한 번 추가될 수 있다.

### 4.3 주요 쓰기 API

| API | SQL |
|---|---:|
| 게시글 작성 | 3 |
| 댓글 작성 | 4 |
| 댓글 수정 | 3 |
| 좋아요 추가 | 5 |
| 좋아요 삭제 | 5 |
| 댓글 삭제 | 4 |
| 게시글 삭제 | 2 |

쓰기 요청은 사용자·게시글·좋아요 존재 확인과 원본 행 변경, 게시글 카운터 변경을 같은
트랜잭션에서 처리하므로 읽기 API보다 SQL 수가 많다. 이번 테스트에서는 정합성 유지에
필요한 쿼리로 판단하고 별도 최적화하지 않았다.

| 시나리오 | 요청 수 | 성공 | 실패 | 평균 | p95 | 최대 |

읽기 시나리오의 엔드포인트별 결과 중 주요 값은 다음과 같다.

| API 그룹 | 요청 | 평균 | p95 |
|---|---:|---:|---:|
| 게시글 목록 | 80 | 52.6ms | 87.4ms |
| 게시글 상세 | 20 | 6.3ms | 10.1ms |
| 댓글 목록 | 20 | 5.1ms | 7.0ms |
| 좋아요 모아보기 | 20 | 9.1ms | 10.9ms |

테스트 중 시스템 상태:

```text
메모리 여유 비율: 34~36%
CPU idle:          약 49~59%
안전 기준 중단:    없음
```

## 6. 결론

- 공개 게시글 목록은 페이지 크기와 관계없이 2 SQL로 고정됐다.
- 로그인 목록은 현재 페이지 좋아요 여부 조회를 포함해 3 SQL로 고정됐다.
- 인기순은 좋아요 GROUP BY 없이 `posts.like_count`로 정렬한다.
- 게시글 상세는 조회수 원자적 UPDATE를 포함해 공개 2 SQL, 로그인 3 SQL이었다.
- 동일한 5만 게시글 데이터에서 읽기 200회와 쓰기 60회가 모두 성공했다.
- 테스트 중 시스템 안전 기준을 넘지 않았다.

이번 결과는 로컬 단일 실행 결과이므로 운영 환경의 최대 처리량을 의미하지 않는다.
이번 테스트의 핵심은 절대적인 응답시간보다 데이터와 페이지 크기가 증가해도 목록 SQL
수가 증가하지 않는 것을 확인한 데 있다.
